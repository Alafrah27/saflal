## Friend-request backend implementation

- api.friendRequests.sendFriendRequest({ receiverId }), acceptFriendRequest({ requestId }), and rejectFriendRequest({ requestId }) return { requestId, status }. IDs identify Convex documents (_id), not users.userId handles or MongoDB records.
- Send validates an active recipient, self-requests, existing friendships, and both-direction blocking. Duplicate outgoing pending sends reuse the original request; a pending incoming request requires explicit acceptance. Rejected/cancelled history is preserved when a fresh request is sent.
- Only the authenticated receiver can accept/reject. Acceptance checks the active sender and blocking, then creates a sorted-ID friendship and updates the request together. Existing friendships in either orientation are reused. Same-decision retries make no writes; opposite or cancelled decisions fail.
- Rejection remains available after sender deletion, inactivity, or blocking and never deletes friendships. Foreign and nonexistent request IDs share a generic unavailable error.
- getPendingFriendRequests({ paginationOpts }) uses by_receiver_status, descending order, 1-100 page sizes, and a 100-row pagination read ceiling. Return standard cursor/split metadata and minimal sender profiles (fullName, optional imageUrl), or sender: null for deleted profiles.
- getFriendshipStatus({ userId }) reports none, outgoing_pending, incoming_pending, or friends. Only pending statuses contain a requestId; third-party relations and reverse-block decisions are not exposed.
- No cancel/unfriend endpoint, contacts-list migration, UI changes, push integration, dependencies, production deployment, or existing-data migration is included. The authentication mismatch remains a separate issue.
