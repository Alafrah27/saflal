## Blocking backend (2026-10-15)

The full current schema was reviewed: users, blockedUsers, friendRequests, friendships, chats, chatMembers, messages, devices, and calls. No schema changes were needed. blockedUsers already stores blockerId, blockedId, and createdAt with by_blocker and by_pair indexes.

Four public functions live in convex/blockedUsers.js. All require an active application profile via requireUser, which looks up the verified Clerk subject using users.by_clerk_id. Public arguments accept a target users ID or pagination options, never a blocker ID. blockUser validates target existence and rejects self-blocking; blockUser/unblockUser return the resulting caller-owned status and are idempotent.

getBlockingStatus queries only the caller-to-target pair. getBlockedUsers pages only the caller's block records, newest first by indexed creation order, and projects each to { _id, blockedId, createdAt, user }, where user contains fullName and optional imageUrl or is null after target deletion. No Clerk identifiers, bio, presence information, reverse-block status, or third-party lists are returned. The query preserves native cursor/endCursor/id/split behavior while enforcing a maximumRowsRead ceiling of 100 and page-size bounds of 1-100. Smaller positive client read limits remain supported; invalid read limits are rejected.

convex/lib/blocking.js exports ordinary server helpers, not registered queries, mutations, or actions. hasBlockingRelationship checks indexed records in both directions and is intended for future communication authorization. Blocking currently writes only blockedUsers; existing history, friendships, requests, and calls are preserved. Mobile UI and communication/notification enforcement remain deferred.

The indexed read and conditional insert execute together in a Convex mutation transaction. Handler tests verify sequential idempotence; live concurrent conflict/retry behavior has not been verified against a deployment. See official [function authentication](https://docs.convex.dev/auth/functions-auth) and [pagination](https://docs.convex.dev/database/pagination) guidance.

The earlier username/userId schema discrepancy was resolved by the user's explicit fullName-only instruction. Existing development usernames were removed through a backed-up, bounded internal migration; identifiers and relationship references were preserved.

## Friend-request backend (2026-10-15)

convex/friendRequests.js adds five authenticated endpoints using the unchanged friendRequests and friendships schemas. requireUser resolves the active caller from Clerk identity; no public endpoint accepts a sender/acting-user ID. receiverId/userId arguments refer to Convex users._id, never a display name. Public arguments and response shapes have Convex validators, and JavaScript is checked with TypeScript.

Request history is append-only on resend after rejection/cancellation: the latest record in each direction comes from by_pair with descending indexed .first() lookups. A duplicate outgoing pending send reuses its ID; an incoming pending request produces INCOMING_REQUEST_PENDING and requires explicit acceptance. Existing friendship pairs prevent new sends. Missing/inactive/blocked targets share USER_UNAVAILABLE; reverse blocking is never disclosed as a separate reason.

Only the receiver can decide a request; foreign and missing IDs share REQUEST_UNAVAILABLE. Pending acceptance verifies an active sender and both-direction blocking, looks for either existing friendship orientation, inserts a canonical sorted-ID friendship if necessary, and patches accepted/updatedAt in one mutation transaction. Completed same-decision retries are no-ops even if communication eligibility later changes; they do not restore missing friendships. Opposite decisions and cancelled requests cannot transition. Rejection does not require a surviving/active sender or unblocked relationship and leaves friendship records intact.

getPendingFriendRequests uses by_receiver_status for the caller's incoming pending records, descending creation order, page sizes 1-100, and maximumRowsRead capped at 100. It preserves native cursor/endCursor/id/split metadata and returns { _id, senderId, receiverId, status, createdAt, updatedAt, sender }. sender is { fullName, imageUrl? } or null after deletion; no Clerk IDs, bio, or presence are returned. Existing blocked/inactive-sender requests remain dismissible.

getFriendshipStatus checks only the caller's relationship with the target. It returns none/friends or outgoing_pending/incoming_pending with a requestId, without reading blockedUsers or exposing reject/cancel history. A block does not delete existing friendships. The earlier server-only hasBlockingRelationship helper is now used by the new send/accept endpoints, while legacy APIs remain unchanged.

Only friendRequests/friendships are written. No chats, messages, calls, push notifications, or UI workflows are added. Atomicity follows the official [Convex transaction model](https://docs.convex.dev/functions/mutation-functions); pagination follows the official [pagination guide](https://docs.convex.dev/database/pagination). Handler tests verify permissions and sequential behavior but do not prove live transactions/realtime/cursor validation.

## Direct-chat backend (2026-10-16)

convex/chats.js exposes getOrCreateDirectChat({ userId }), getChat({ chatId }), and getMyChats({ paginationOpts }). Every operation resolves an active profile through requireUser and verified Clerk identity. Creation/reuse requires an existing active recipient, an accepted friendship in either stored orientation, and no block in either direction. Self-chats are rejected; missing, inactive, blocked, and nonfriend recipients share USER_UNAVAILABLE.

chats.directPairKey is optional for historical compatibility. New chats store JSON.stringify of the two lexically sorted Convex user IDs and use by_direct_pair for bounded pair lookup. Pair absence checking and insertion of the chat plus two memberships execute in one [Convex mutation transaction](https://docs.convex.dev/functions/mutation-functions). Defaults are disappearingMessages=false, isArchived=false, and isMuted=false; all timestamps are server-generated. A repeat reuses the ID without writes. Duplicate pair records or invalid memberships fail safely without repair.

Reads require exactly one caller membership and exactly two distinct participants, using by_chat_user.take(2) and by_chat.take(3). A present pair key must match those participants. Missing/foreign/invalid chat IDs share CHAT_UNAVAILABLE. Membership preserves history access after blocking, loss of friendship, or peer inactivity/deletion. Reads do not disclose reverse blocks or presence.

Returned views contain chatId, type, disappearingMessages, createdAt, updatedAt, optional lastMessageId/lastMessageAt, peer, and membership. peer is {_id, fullName, imageUrl?} or null after deletion. membership contains only the caller's joinedAt, isArchived, isMuted, and optional lastReadAt. Clerk IDs, pair keys, bio, presence, and the other member's settings are excluded.

getMyChats paginates caller-owned memberships through by_user in descending membership creation order, including archived chats. Page sizes are 1-100; pagination maximumRowsRead is capped at 100, with additional bounded membership/profile enrichment per row. Orphaned or inconsistent rows are omitted without altering Convex cursor/split metadata. A full page can still require a further request to reach isDone=true. This is creation ordering, not message-activity ordering.

The legacy chat screens, message transport, deletion flow, and calling remain unchanged. No new message/read-receipt/unread-count or preference/expiration functions are implemented. New writes affect chats/chatMembers only. Future imports of historical keyless chats require a reviewed backfill before enabling creation against those records.
# Devices / ordinary push backend recovery — 2026-10-16

Mutations claim at most 100 sends and 100 receipt lookups per tick; actions submit bounded Expo batches with a ten-second timeout. ## Strict shared message schema — 2026-10-16

The existing messages table now has a top-level discriminated union: type=text requires text and excludes audio fields; type=audio requires audioStorageId and audioDuration (seconds) and excludes text. Both retain chatId, senderId, the existing sent/delivered/read status union, createdAt/updatedAt, and optional expiresAt. Indexes by_chat, by_chat_created, and by_expires_at are unchanged. All other tables, including chats.disappearingMessages and the existing false creation default, are preserved. This uses the supported [Convex document union](https://docs.convex.dev/database/schemas) and adds no table, endpoint, or dependency.

This schema enforces shape only. Future mutations must enforce content limits, positive finite duration, trusted timestamps, identity/membership/block rules, retry idempotency, and private authorized storage references. A typed ID alone does not prove existence/ownership. See [message.md](../message.md) for the contract and pending runtime checklist.

Future expiry uses a message's immutable assigned deadline, not the current conversation setting. New text/audio messages sent while enabled get createdAt + 2,592,000,000 milliseconds; disabled sends omit expiresAt. Toggling never rewrites historical messages. Reads must hide expired records independently of cleanup, including chat previews/unread state, and preserve bounded cursors. Time passing alone does not invalidate a subscribed query, so timely rendering/invalidation needs explicit implementation. Bounded cron cleanup must exclude missing deadlines and safely remove only authorized, unneeded audio objects while preserving consistent chat metadata and recoverable retries. Either member may toggle with server authorization; both must see reactive status and server-owned notices. Notice representation is deferred, not a third schema variant added in this delivery.

No runtime messaging/expiration/cleanup/UI feature or deployment is introduced by this schema delivery. External screenshots, downloads, backups, and other copies cannot be removed by deleting within Saflal.
